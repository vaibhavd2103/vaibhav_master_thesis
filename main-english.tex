\section*{Abstract}
% ---------------------------------------------------------------

Multiphysics simulation software such as preCICE is a powerful enabler of partitioned coupled
simulations, yet its configuration complexity and steep learning curve present a considerable
barrier to new and occasional users.
This thesis investigates how an intelligent, context-aware assistant can lower this barrier by
integrating natural-language interaction directly into the local preCICE simulation environment.

General-purpose language model assistants lack grounded access to local project state,
configuration files, and runtime logs, and are therefore unable to provide actionable,
context-specific guidance.
To address this gap, two complementary prototypes were designed and implemented.
The first is a preCICE-focused \gls{mcp} server that exposes project discovery, configuration
inspection, log analysis, a dual lexical-and-semantic knowledge base built from the preCICE
documentation, forum, and issue tracker, and a wrapper around the official \texttt{precice-cli},
to any \gls{mcp}-compatible client.
The second is a self-contained agentic client built with LangGraph that runs a ReAct-style
tool-calling loop, combines a purpose-built retrieval pipeline with the same class of project,
configuration, and log tools, and can drive the \gls{mcp} server as a subprocess.
Both prototypes ground the language model in the user's actual project state rather than
relying on its training data alone.

The prototypes are evaluated through functional testing and a scenario-based comparison
spanning simulation setup, configuration error detection, and log analysis, contrasting
usability, response accuracy, local integration, and extensibility against each other and
against an ungrounded baseline.
Accuracy is assessed across two retrieval modes, several language models of differing
capability, and question sets of increasing difficulty.

\hl{Results indicate measurable improvements over an ungrounded baseline on preCICE-related
tasks, suggesting that grounded, tool-integrated language-model assistants can meaningfully
narrow the usability gap in scientific simulation software and point toward an architecture
that generalises to other simulation frameworks.}

\chapter{Introduction}\label{sec:introduction}
%%% ===============================================================

Multiphysics simulations are an indispensable tool across modern engineering and science,
enabling the study of coupled physical phenomena that cannot be captured by single-physics
models alone.
Setting up and operating such simulations requires integrating multiple solvers, managing data
exchange between them, and carefully configuring coupling parameters which is a process that demands
deep expertise and considerable time even from experienced practitioners \cite{chourdakis2022precice}.

preCICE is a widely adopted open-source coupling library that manages precisely this
complexity: it handles data mapping, communication, and synchronization between independent
solver codes \cite{chourdakis2022precice}.
However, the very breadth of its capabilities, which is configuration files, command-line tools,
documentation that spans dozens of pages, and a rich community forum, creates an information
overload that is particularly challenging for new users.
Mistakes in configuration files can lead to simulation failures, and diagnosing issues
from log output requires familiarity with preCICE internals that takes time to acquire.

Recent advances in \glspl{llm} and tool-integration frameworks have opened a new possibility:
an intelligent assistant that operates locally within a user's simulation environment,
understands project structure and configuration state, and communicates with the user in
natural language.
The \gls{mcp} \cite{mcp2024spec} provides a standardized mechanism for connecting \glspl{llm}
to local tools and data sources, making such integration practically feasible.

This thesis presents \emph{preCICE-AI}, an intelligent assistant designed to integrate with
the preCICE ecosystem. The next sub-sections introduces the domain context (\Cref{sec:introduction:topic}), 
surveys the state of the art and identifies the knowledge gap (\Cref{sec:introduction:state-of-art}) and 
states the research question (\Cref{sec:introduction:research-question}). After that it
outlines the method adopted (\Cref{sec:introduction:method}) and summarizes the results and their interpretation (\Cref{sec:introduction:results} ).


% ----------------------------------------------------------------
\section{Context and Topic}\label{sec:introduction:topic}
% ----------------------------------------------------------------

Partitioned multi-physics simulation is a paradigm in which separate, specialized solver codes
are coupled at runtime to exchange physical quantities across shared boundaries.
This approach allows reusing mature, validated solvers for individual physics and combining them
to study coupled phenomena such as \gls{fsi}, \gls{cht}, and
electromagnetic-thermal coupling.
The preCICE coupling library \cite{chourdakis2022precice} has become a reference
implementation of this paradigm, offering a rich feature set including \gls{rbf} mapping,
quasi-Newton acceleration, and multi-solver coupling topologies.

Despite its technical maturity, preCICE places a significant cognitive burden on users.
A typical simulation project requires authoring an \gls{xml} configuration file that encodes all
participants, data fields, mappings, coupling schemes, and time-stepping parameters.
The configuration language is expressive but unforgiving: a missing attribute or an incorrectly
spelled participant name will cause the simulation to fail at runtime, sometimes without a
clear error message. These errors could be identified before the runtime, but require knowledge of 
preCICE \gls{cli} and its tooling.
Users must also understand how to invoke preCICE \gls{cli}, interpret log output, and
navigate the documentation to diagnose problems.

\Glspl{llm} have demonstrated strong capabilities in code understanding, question answering
over technical documentation, and guided task completion.
Integrating such models into the simulation workflow, as a locally running assistant with access
to project files and runtime state, could significantly reduce the setup time and error rate
for both new and experienced preCICE users.
This constitutes the general objective of the developer community and science towards which this thesis
contributes: making high-fidelity multi-physics simulation software accessible without sacrificing
the power and flexibility that expert users require.



% ----------------------------------------------------------------
\section{State of the Art}\label{sec:introduction:state-of-art}
% ----------------------------------------------------------------

Several lines of prior work are relevant to the vision of an intelligent assistant for scientific
simulation software.

Intelligent coding assistants such as GitHub Copilot~\cite{chen2021copilot} and Cursor have
demonstrated that \glspl{llm} can provide context-aware code suggestions by operating within
a developer's local file system, yet these tools are designed for general programming tasks
and provide only partial coverage of domain-specific knowledge such as simulation workflows,
coupling configurations, or physical unit constraints~\cite{hou2024largelanguagemodels}.
The \gls{mcp}~\cite{mcp2024spec} establishes a standardised client-server protocol through
which a language model can invoke tools exposed by a local server, enabling access to file
contents, command execution, and structured data queries without transmitting sensitive project
data to a remote service; related work on function-calling \glspl{api} from
Anthropic~\cite{anthropic2024tool} and OpenAI~\cite{openai2024responses} confirms that
language models can reliably incorporate tool results into their responses.
Beyond single-turn tool calling, frameworks such as LangGraph model an agent as a state
machine in which a language-model node and a tool-execution node alternate until the model
produces a final answer, a pattern known as ReAct~\cite{yao2023react}; this graph-based
formulation makes the control flow of a multi-step, tool-using agent explicit and inspectable,
which is valuable both for debugging and for the controlled evaluation undertaken in this thesis.

Prior work on \gls{llm} assistants tailored specifically to simulation software remains sparse:
the Perfetto \gls{mcp} project~\cite{perfettomcp2024} demonstrates tool-based trace analysis
for performance profiling, which is conceptually similar to log analysis in the preCICE context,
but no published work addresses the full workflow of preCICE project setup, configuration
validation, simulation execution, and result analysis through a unified assistant interface.
The gap this thesis targets is therefore a purpose-built, locally integrated assistant that
supports the complete preCICE user workflow from initial configuration to log-based diagnosis,
without requiring deep expertise about the preCICE and its tooling.


% ----------------------------------------------------------------
\section{Research Question}\label{sec:introduction:research-question}
% ----------------------------------------------------------------

Given a local preCICE simulation project consisting of a configuration file, solver source
trees, and runtime log files, the central research question of this thesis is:

\begin{center}
\emph{Can an \gls{llm}-based assistant, grounded through structured tool access and
context-aware retrieval, support preCICE users in completing simulation setup, configuration,
and diagnostic tasks more effectively than ungrounded \gls{llm} interaction?}
\end{center}

This general question is decomposed into the following sub-questions for better understanding and answering them in detail:

\begin{enumerate}[label=\textbf{RQ}\arabic*]
  \item \emph{Tool integration:} Which preCICE tools, data sources, and operations are
        necessary and sufficient for an assistant to support the core user workflow, and how
        can these be exposed via an \gls{mcp} server to an \gls{mcp}-compatible client?
  \item \emph{Context retrieval:} How can documentation and forum knowledge be
        indexed and retrieved at query time to provide accurate, source-attributed answers to
        user questions about preCICE concepts and errors?
  \item \emph{Prototype comparison:} How does an \gls{mcp}-based approach, consumed
        through general-purpose \gls{mcp} clients, compare with a self-contained LangGraph
        agent in terms of usability, accuracy of responses, local integration, development
        complexity, and extensibility?
\end{enumerate}

The evaluation criterion for success is that the assistant can complete a defined set of
representative tasks - including configuration file authoring, error detection, and log
interpretation, with higher accuracy and lower user effort than baseline (unaided \gls{llm}
interaction or documentation search alone).


% ----------------------------------------------------------------
\section{Approach}\label{sec:introduction:method}
% ----------------------------------------------------------------

The thesis follows a design-science research methodology combined with empirical scenario
evaluation, proceeding through six successive phases that move from literature grounding
through implementation to comparative assessment.

The conceptual foundation is established through a structured literature review conducted via
snowball sampling: starting from the primary preCICE publication~\cite{chourdakis2022precice},
reference lists of cited works were followed outward and citation networks traced in reverse,
covering the areas of \gls{llm} tool integration, \gls{mcp}-based server architectures, agent
orchestration frameworks, \gls{rag} pipelines, and prior work on intelligent assistants for
scientific software.
The resulting body of literature informs the design decisions made in all subsequent phases
and is discussed in \cref{sec:background}.

The target domain is then characterised through a documentation-based analysis of the
preCICE architecture, its \gls{xml} configuration language, the official \gls{cli}, and the
content of the documentation, tutorial pages, and Discourse community forum.
Beyond reading, several official tutorial cases were actively set up and executed so that the
configuration workflow, runtime log structure, and likely failure modes could be understood
from direct experience rather than documentation alone.
This analysis identifies which information sources and operations an assistant must support,
and is documented in \cref{sec:problem-exposition}.

The primary prototype is a preCICE \gls{mcp} server exposing five fully implemented tool
groups: project discovery, configuration inspection, log analysis, knowledge-base retrieval,
and a wrapper around the official \texttt{precice-cli}.
Adherence to the \gls{mcp} specification means the server connects without modification to
any compatible client, decoupling the tool layer from the choice of language model or
development interface.
The implementation is described in \cref{sec:mcp-server}.

Both prototypes share a dual-path retrieval pipeline that indexes content from the preCICE
documentation, tutorials, Discourse forum, and GitHub issue tracker, combining a \gls{bm25}
lexical index with pre-computed semantic embeddings stored locally.
At query time, the user's question is encoded via an embedding model
and matched against the local index; results from both paths are merged and re-ranked before
being passed to the language model as context.
This design keeps the knowledge base fully reproducible and offline-capable, with only the
query-encoding step requiring an external call.
The retrieval pipeline is described in \cref{sec:context-retrieval}.

A second prototype built with LangGraph runs a ReAct-style tool-calling loop behind a locally
hosted browser interface and can additionally drive the \gls{mcp} server as a subprocess,
allowing the evaluation to isolate the contribution of the \gls{mcp} abstraction layer from the
underlying tools and retrieval pipeline that both prototypes share.
This prototype is described in \cref{sec:claudecode-approach}.

Finally, a scenario-based evaluation spanning simulation setup, configuration error detection,
and log analysis is executed across three language models of differing capability\hl{: Claude
Sonnet, GPT-5 Codex, and Mistral Mini,} and under two knowledge-base configurations,
lexical and semantic retrieval.
Both prototypes are compared against each other and against an unassisted baseline, with
narrowly defined questions assessed through similarity-based scoring and open-ended queries
through manual qualitative review.
The evaluation design and results are presented in \cref{sec:evaluation}.


% ----------------------------------------------------------------
\section{Findings}\label{sec:introduction:results}
% ----------------------------------------------------------------

The thesis provides a set of findings that are mentioned in the following sections and also in detail 
in \cref{sec:evaluation} and \cref{sec:evaluation:results}.

\section*{Results}

The \gls{mcp} server prototype has been implemented \hl{and validated with all five tool groups
(project, configuration, log, knowledge base, and \gls{cli} wrapper) returning correct results
on a set of representative preCICE projects.
Functional testing shows that all implemented tools respond correctly to well-formed requests
and return structured error messages for invalid inputs.}
The LangGraph prototype has also been implemented as a self-contained agent with its own
basic tool-set, integration with the \gls{mcp} server for retrieval pipeline and advanced tools, 
and has been observed to complete representative preCICE project-inspection and documentation-lookup tasks end to end.
\hl{Preliminary indexing of the preCICE documentation confirms that semantic search returns
relevant passages with a precision of XYZ on a sampled set of 20 queries.}
A full quantitative evaluation across all scenarios, both prototypes, and combinations of knowledge-base 
mode, model capability, and question difficulty is described in \cref{sec:evaluation}.

\section*{Interpretation}

The successful implementation of the \gls{mcp} server confirms that the preCICE toolchain
can be exposed to a large-language-model assistant through a lightweight, standards-based protocol
without requiring modifications to preCICE itself.
The separation of tool groups corresponds to the distinct phases of the preCICE user workflow,
suggesting that the server design is aligned with real usage patterns.
The development of a second, architecturally independent prototype that reuses the same class of
tools shows that the underlying tool design is not an artifact of any single client or
orchestration framework, and can be integrated to any agentic client.
The retrieval component is expected to address the accuracy shortfall observed in ungrounded
\gls{llm} interaction on preCICE-specific questions.
\hl{After complete comparison of both prototypes against the evaluation criteria, determined that the \gls{mcp}
approach is comparatively a better solution to close the gap between using preCICE and understanding
preCICE in-depth. Likewise, the semantic retrieval from the knowledge base performs much better in answering
user queries than the lexical approach, and the high thinking models with larger context-window and more
parameters provides more adequate deliverables by choosing tools and incorporating tool responses more accurately.}

\chapter{Background}\label{sec:background}
%%% ===============================================================

This chapter provides the technical background required to understand the design and
implementation of preCICE AI. First it introduces the preCICE coupling library and its ecosystem (\Cref{sec:background:precice}),
then large language models and relevant interaction paradigms (\Cref{sec:background:llm}) and describes the \gls{mcp} (\Cref{sec:background:mcp}).

\section{The preCICE Coupling Library}\label{sec:background:precice}
% ----------------------------------------------------------------

preCICE (Precise Code Interaction Coupling Environment) is an open-source library designed
for partitioned multi-physics simulations~\cite{chourdakis2022precice}.
Rather than providing its own solvers, it follows a library approach in which existing,
independently developed solver codes are each instrumented with a small set of preCICE
\gls{api} calls that handle initialisation, data exchange, and time-step synchronisation.
A typical simulation consists of two or more \emph{participants}, each running as an
independent process, exchanging scalar or vector \emph{data} fields over shared
\emph{meshes} at their common boundaries.
preCICE coordinates this exchange transparently, supporting both serial and parallel coupling
schemes, explicit and implicit time-stepping, and a range of spatial mapping methods including
nearest-neighbour, nearest-projection, and \gls{rbf} mapping~\cite{chourdakis2022precice}.
The entire coupling behaviour is declared in a single \gls{xml} configuration file, conventionally
named \texttt{precice-config.xml}, which specifies the participants, meshes, data fields,
mapping methods, coupling schemes, and logging settings in one place.
A dedicated \gls{cli} complements the library, offering utilities for validating a configuration
file before a run, listing declared participants, and inspecting mesh statistics, while runtime
log files record coupling convergence, mapping quality, and timing information for
post-hoc analysis.

The preCICE ecosystem extends beyond the core library through a broad set of community
resources.
The project website hosts comprehensive documentation covering the configuration reference,
\gls{api} documentation, and step-by-step tutorials for common coupling scenarios, all
maintained alongside the library source~\cite{chourdakis2022precice}.
The Discourse forum at \url{https://precice.discourse.group/} serves as the primary
community support channel, with thousands of threads addressing configuration questions,
adapter integration issues, and debugging advice accumulated over years of active use.
\hl{Together, these resources form a rich but distributed knowledge base that a new user must
navigate in parallel with the practical task of setting up a simulation, a combination that
motivates the assistant-based approach developed in this thesis.}

\section{Large Language Models and Tool Use}\label{sec:background:llm}
% ----------------------------------------------------------------

\Glspl{llm} are neural sequence models trained on large corpora of text that have demonstrated
strong capabilities in natural-language understanding, code generation, and instruction
following~\cite{brown2020gpt3}.
At inference time, a model receives a \emph{context window} which is a contiguous sequence of
tokens that typically includes a system prompt describing the model's role and available tools,
any prior conversation turns, and the user's current message.
The model then produces a continuation of that sequence, token by token, according to the
probability distribution it learned during training.
Crucially, the context window is the only information the model can act on at any given moment:
it has no persistent memory between separate calls and no inherent ability to reach outside
the conversation unless explicitly provided with mechanisms to do so.

One such mechanism is \emph{tool use}, also referred to as function calling, which is the
capability most directly relevant to this thesis.
Rather than being limited to producing free text, a model that supports tool use can emit a
structured tool-call request, specifying a function name and a set of typed arguments; 
when it determines that answering the user's query requires information or an action beyond
what is already present in its context.
The host application intercepts this request, executes the corresponding function, and returns
the result as a new entry in the conversation; the model then reads that result and continues
generating its response, potentially issuing further tool calls before producing a final answer.
In practice, the model learns when and how to call tools from the descriptions provided in
the system prompt: a well-written tool description functions almost like documentation, telling
the model what the tool does, what its parameters mean, and under what circumstances it
should be invoked~\cite{anthropic2024tool}.

This single-turn interaction pattern i.e. one user message, one or more tool calls, one
response, is sufficient for many tasks, but more complex workflows require a model to
reason across multiple steps, revise its plan in response to unexpected tool outputs, and
maintain a coherent thread of work over an extended sequence of calls.
This is the motivation behind \emph{agentic} architectures, in which the model is placed
inside a loop that alternates between reasoning and acting until a stopping condition is met.
The ReAct pattern~\cite{yao2023react}, for instance, prompts the model to interleave explicit
reasoning steps with tool-call actions, making its decision process inspectable and easier to
debug.

\section{The Model Context Protocol}\label{sec:background:mcp}
% ----------------------------------------------------------------

The \gls{mcp} \cite{mcp2024spec} is an open protocol that standardizes communication between
\gls{llm} applications (clients) and local tool servers.
An \gls{mcp} server exposes a set of \emph{tools}, \emph{resources}, and \emph{prompts}
via a \gls{json}-\gls{rpc} interface over standard \gls{io} or \gls{http}.
The client discovers available tools through a capability negotiation handshake and invokes
them by name with typed parameters.

\begin{definition}[MCP Tool]
  An \gls{mcp} tool is a callable function exposed by an \gls{mcp} server, described by a
  name, a human-readable description, and a \gls{json} Schema specifying its input parameters
  and return type.
\end{definition}

The key advantage of \gls{mcp} over ad-hoc function-calling integrations is standardization:
any \gls{mcp}-compatible client can interact with any \gls{mcp}-compatible server without
custom glue code.
Several widely used coding assistants, including Claude Code \cite{anthropic2024claudecode},
Claude Desktop, Codex, Cursor, and Windsurf, support \gls{mcp} natively, which allows a single
server implementation to reach all of them without client-specific adaptation.

Because an \gls{mcp} server is reachable by any conforming client, the same server-side tool
surface can also be exposed to an application that a project builds and controls in full, rather
than to a third-party assistant, resulting in no Vendor-Lockin.
This is the role that the \gls{mcp} server designed in this thesis plays for the LangGraph
prototype described in \cref{sec:claudecode-approach}: the server is consumed both as an
installed tool provider for external \gls{mcp} clients and as a subprocess driven directly by a
custom agent runtime.

\section{Agent Orchestration and the ReAct Pattern}\label{sec:background:agents}
% ----------------------------------------------------------------

Exposing tools to a language model, whether through \gls{mcp} or a native function-calling
\gls{api}, only solves half of the integration problem.
The other half is the control flow that decides when to call a tool, how to incorporate its
result, and when enough information has been gathered to produce a final answer.
This control flow is commonly referred to as an \emph{agent loop}.

A widely adopted pattern for this loop is ReAct, short for ``reasoning and acting''
\cite{yao2023react}, in which the model alternates between producing a reasoning step and
selecting an action, observes the result of that action, and continues until it emits a final
answer instead of a further action.
Applied to tool-calling \glspl{llm}, the pattern reduces to a simple cycle: the model either
returns a plain-text answer, in which case the loop terminates, or it returns one or more tool
calls, which are executed and whose results are appended to the conversation before the model
is invoked again.

\begin{definition}[Agent Loop]
  Given a language model $p_\theta$, a fixed set of tools $\mathcal{T}$, and a conversation
  history $h$, an agent loop repeatedly computes $a = p_\theta(h)$, where $a$ is either a final
  answer or a tool invocation $t \in \mathcal{T}$ with arguments; in the latter case the tool
  result is appended to $h$ and the loop continues.
\end{definition}

Frameworks such as LangGraph make this loop explicit by modelling it as a directed graph over
named nodes and conditional edges, rather than as an implicit loop hidden inside a client
application.
A typical two-node instantiation consists of an \emph{agent} node, which invokes the language
model with the current conversation and the bound tool schemas, and a \emph{tools} node, which
executes any tool calls the model has requested and returns their results to the agent node.
A conditional edge inspects the agent node's output after every invocation: if it contains tool
calls, control passes to the tools node; otherwise the graph terminates.
This explicit, inspectable structure is one of the reasons LangGraph was chosen for the second
prototype developed in this thesis, described in \cref{sec:claudecode-approach}: the same graph
can be instrumented to stream intermediate tool calls to a user interface and to log every
transition for later analysis, both of which are used in the evaluation reported in
\cref{sec:evaluation}.

\section{Retrieval-Augmented Generation}\label{sec:background:rag}
% ----------------------------------------------------------------

\Gls{rag} \cite{lewis2020rag} is a technique that augments an \gls{llm}'s response generation
with relevant passages retrieved from an external knowledge base.
The standard pipeline consists of an offline indexing phase, in which documents are chunked,
encoded as dense vectors using an embedding model, and stored in a vector index; and an online
retrieval phase, in which a query is encoded and used to retrieve the $k$ nearest document
chunks by cosine similarity.
The retrieved chunks are prepended to the \gls{llm}'s context window as grounding evidence.

\gls{rag} is particularly valuable for domain-specific question answering because it allows the
\gls{llm} to cite specific source passages, reducing hallucination and improving factual accuracy
on topics not covered in the model's training data.
For preCICE AI, \gls{rag} enables the assistant to generate its responses from the official
documentation, tutorials and community-validated forum answers.

\begin{definition}[Retrieval-Augmented Generation]
  Given a user query $q$ and a corpus $\mathcal{D}$ of documents, \gls{rag} retrieves a set
  $\mathcal{R} = \{d_1, \ldots, d_k\} \subseteq \mathcal{D}$ of relevant passages and conditions
  the language model $p_\theta$ on both $q$ and $\mathcal{R}$:
  $\hat{y} = \arg\max_y p_\theta(y \mid q, \mathcal{R})$.
\end{definition}

\section{Related Work}\label{sec:background:related}
% ----------------------------------------------------------------

The most direct predecessors of the work presented in this thesis are general-purpose coding
assistants such as GitHub Copilot~\cite{chen2021copilot}, which demonstrated that \glspl{llm}
trained on code can provide useful, context-aware inline completions within a developer's
editor.
Extensions such as Copilot Chat brought conversational interaction into the same environment,
yet both tools remain oriented toward general programming tasks and provide only partial
coverage of domain-specific knowledge such as simulation workflows or coupling configurations,
as discussed in \cref{sec:introduction:state-of-art}.
The work that comes closest to preCICE AI from the scientific software side is
ChemCrow~\cite{bran2023chemcrow}, an \gls{llm}-based agent augmented with a suite of
chemistry tools that together allow the model to reason about molecular structures and
laboratory procedures.
The architectural analogy is direct - a language model given access to domain tools so that
it can act on, rather than merely describe, the user's problem; but the target domain,
evaluation methodology, and tool design are entirely different, and no comparable system
exists for multi-physics coupling software.

The protocol layer on which the primary prototype is built, the \gls{mcp}~\cite{mcp2024spec},
has attracted a growing body of work examining both its applicability and its risks.
On the applicability side, the Perfetto \gls{mcp} project~\cite{perfettomcp2024} demonstrates
a domain-specific \gls{mcp} server for performance trace analysis, establishing that the
protocol is practical for scientific tooling beyond general software development.
On the risk side, \citeauthor{hou2025mcplandscape}~\cite{hou2025mcplandscape} map the
\gls{mcp} server lifecycle and derive a taxonomy of threat scenarios that arise when tool
descriptions, arguments, or return values are not treated as trusted input by the client.
\citeauthor{hasan2025mcpfirstglance}~\cite{hasan2025mcpfirstglance} conduct a large-scale
empirical study of open-source \gls{mcp} servers and find that a non-trivial share exhibit
weaknesses such as command-injection-prone implementations or insufficiently constrained
file-system access.
\citeauthor{wang2025mcptox}~\cite{wang2025mcptox} go further by introducing a benchmark
for tool-poisoning attacks, in which a malicious server misleads an agent through its tool
descriptions rather than through the arguments it returns, underlining that the trust boundary
in an \gls{mcp} deployment extends to the server author and not only to the end user.
These findings directly motivate the conservative, allowlist-based command-execution design
and the read-mostly posture of the configuration and log tools implemented in this thesis.

Assessing whether an agent selects and invokes the correct tool for a given task is itself an
active research problem.
\citeauthor{patil2023gorilla}~\cite{patil2023gorilla} show that general-purpose language models
frequently hallucinate function names or arguments when calling an unfamiliar \gls{api},
motivating retrieval-augmented or schema-guided tool selection.
The Berkeley Function-Calling Leaderboard~\cite{patil2025bfcl} formalises this into a
reproducible methodology that scores both the syntactic correctness of a tool call and, where
possible, the correctness of its executed effect; this approach informs the accuracy metrics
used in the evaluation in \cref{sec:evaluation}.
\citeauthor{wang2025mcpbench}~\cite{wang2025mcpbench} extend this style of evaluation to
multi-step tasks executed against real \gls{mcp} servers, which is closer in spirit to the
end-to-end preCICE scenarios evaluated in this thesis than single-call benchmarks.
On the orchestration side, the ReAct pattern of interleaved reasoning and acting~\cite{yao2023react}
underlies most contemporary tool-calling agent runtimes, including the graph-based
orchestration provided by LangGraph~\cite{langgraph2024} that is used to implement the second
prototype described in \cref{sec:claudecode-approach}.

The retrieval component of both prototypes are based on a well-established line of work in
\gls{rag}.
\citeauthor{gao2023retrieval}~\cite{gao2023retrieval} survey the field and identify the key
design choices, i.e. chunking strategy, embedding model, and retrieval depth; which most
strongly affect quality of the downstream answer, all of which are examined in the pipeline design
described in \cref{sec:context-retrieval}.
\citeauthor{es2023ragas}~\cite{es2023ragas} propose a reference-free evaluation methodology
built around faithfulness, answer relevance, and context relevance, which addresses the
qualitative assessment criteria applied to the open-ended questions in the evaluation.

Taken together, this body of work establishes the building blocks on which preCICE AI rests,
but no existing system combines \gls{mcp}-based local tool integration with domain-specific
documentation and forum retrieval for a multi-physics coupling library, targets the complete
user workflow from initial setup to diagnostic analysis, or implements the same class of tools
under two different orchestration models so that the choice of client architecture can be
examined as an independent variable.

\section{Context and User Workflow Understanding}\label{sec:problem-exposition:context-understanding}
% ----------------------------------------------------------------

A typical preCICE user workflow proceeds through the following phases, each of which presents
distinct challenges amenable to assistant support.

\paragraph{Phase 1: Project initialization.}
The user creates a directory structure containing solver source code (or adapter code), a
preCICE configuration file, and run scripts.
The configuration file must correctly declare all participants, meshes, and data fields that the
solvers expect.
Errors at this stage, such as mismatched participant names between the configuration and the
solver adapter are common and difficult to diagnose without deep knowledge of both the
preCICE \gls{api} and the specific adapter.

\paragraph{Phase 2: Configuration authoring and validation.}
The user writes or modifies the \texttt{precice-config.xml} file.
This involves choosing an appropriate coupling scheme (serial explicit, parallel implicit, etc.),
selecting a spatial mapping method, and tuning convergence parameters.
The official documentation provides reference material, but finding the right configuration for
a specific physical scenario requires understanding trade-offs that are not always clearly
documented.

\paragraph{Phase 3: Simulation execution and monitoring.}
The user launches the coupled simulation, which involves starting each participant in a
coordinated manner.
preCICE logs runtime information including convergence history, mapping quality indicators,
and timing data.
Interpreting these logs requires familiarity with preCICE internals.

\paragraph{Phase 4: Post-hoc analysis and debugging.}
When a simulation fails or produces unexpected results, the user must diagnose the cause from
log files, configuration inspection, and if necessary, re-reading the documentation or
searching the Discourse forum.
This is often the most time-consuming phase, particularly for users who encounter an error
for the first time.

\paragraph{\glspl{llm} have shown good results in configuring files, understanding error messages, and overall
better analysis and debugging in different projects. Based on these findings it suggests that 
an intelligent assistant is most valuable in phases 2 and 4, where knowledge-intensive
tasks like configuration decision-making and error diagnosis, are the primary bottlenecks in preCICE projects.}

\section{Data Understanding}\label{sec:problem-exposition:data-understanding}
% ----------------------------------------------------------------

The preCICE ecosystem exposes several distinct data sources that users regularly use when
setting up, running, and debugging simulations. Understanding what each source contains and
how it can be accessed informs which of them are incorporated into preCICE AI and which are
left outside its scope.

\noindent\textbf{Local project files.} A preCICE project directory typically contains the
configuration file, solver-specific configuration files, build scripts, and run scripts.
These files are available on the user's local file system and are the most immediately
relevant source for any project-specific query, since they reflect the exact state of the
simulation the user is currently working on.

\noindent\textbf{preCICE log files.} preCICE writes structured log files during simulation
execution, including convergence data per iteration, watchpoint values, timing breakdowns, and
error messages. Log files follow the naming convention
\texttt{precice-<participant>-<type>.log} and are located in the directory from which the
simulation was launched.

\noindent\textbf{preCICE documentation.} The official documentation at \url{https://precice.org/}
consists of approximately 80 Markdown pages covering the configuration reference, \gls{api}
documentation, tutorials, and troubleshooting guides. The documentation is publicly available
and can be crawled and indexed offline.

\noindent\textbf{preCICE Discourse forum.} The Discourse forum contains several thousand
threads representing community knowledge accumulated over years of preCICE usage. Forum
posts contain user-reported problems, expert answers, and configuration examples, and are
publicly accessible via the Discourse \gls{api}.

\noindent\textbf{GitHub issue tracker and pull requests.} The preCICE source repository has
an active issue tracker and pull-request history that records reported bugs, feature
discussions, and the reasoning behind past design decisions. This content is publicly accessible
through the GitHub \gls{api} and frequently contains troubleshooting detail that complements
the curated documentation.

\noindent\textbf{preCICE configuration schema.} The preCICE \gls{xml} schema formally
specifies valid configuration elements, attributes, and their types. Rather than reimplementing
schema validation independently, the assistant wraps the configuration-checking subcommand
of the official \texttt{precice-cli}, so that validation results always match the behaviour of
the reference toolchain and track future schema changes automatically.

\noindent\textbf{Command execution boundary.} Beyond passively read data, the assistant is
also permitted to execute a narrow, explicitly allowlisted set of read-oriented shell commands
inside a project directory, such as listing files or inspecting a run script, so that it can
answer questions that require broader context than any single file provides. Commands are
checked against an allowlist of safe prefixes and a blocklist of destructive patterns before
execution, and all file-system access is confined to the configured project directory.
\Cref{sec:mcp-server:implementation} details this safety mechanism.

Of these sources, the solution incorporates all of them to varying degrees. Local project files
and log files are accessed directly at query time through the project and log tool groups,
making them the most tightly integrated source and the primary basis for project-specific
answers. The documentation, Discourse forum, and GitHub issue tracker are indexed offline
into the knowledge base and retrieved at query time, meaning their content is always available
even without a network connection at the time of the query; the trade-off is that the index
reflects a snapshot of these sources at the time of indexing and must be periodically
refreshed to remain current. Configuration schema validation is delegated entirely to the
official \gls{cli} rather than reimplemented, which guarantees correctness but introduces a
runtime dependency on a working preCICE installation.

\section{Detailed Research Sub-Questions}\label{sec:problem-exposition:research-problems}
% ----------------------------------------------------------------

Based on the context and data analysis above, the research questions on tool integration, 
context retrieval, and prototype comparison described in \cref{sec:introduction:research-question} are wide and can be decomposed into multiple sub questions for answering and designing solution more efficiently.
The research questions can be elaborated as follows.

\textbf{RQ1 Tool integration:} Which preCICE tools, data sources, and operations are necessary and
sufficient for an assistant to support the core user workflow, and how can these be exposed via an
\gls{mcp} server?
\begin{enumerate}[label=RQ1.\arabic*]
  \item Which project-level operations (file reading, participant listing) are
        needed to answer the most common user queries?
  \item Which configuration-level operations (structured inspection, human-readable
        summarization, schema validation via the reference \gls{cli}, safe backup before
        modification) are needed?
  \item Which log-level operations (error extraction, convergence detection) are needed?
  \item What is the appropriate granularity and return format for \gls{mcp} tool outputs to
        maximize their utility as \gls{llm} context?
\end{enumerate}

\textbf{RQ2 Context retrieval:} How can documentation and forum knowledge be indexed and retrieved at
query time to provide accurate, source-attributed answers to user questions about preCICE concepts
and errors?
\begin{enumerate}[label=RQ2.\arabic*]
  \item How should documentation, tutorial, forum, and issue-tracker content be chunked and
        embedded to maximize retrieval relevance?
  \item How should retrieved passages be integrated into the \gls{llm} prompt to support
        source-attributed answers?
  \item Under which conditions does semantic (embedding-based) retrieval outperform lexical
        (keyword-based) retrieval, and does this depend on question difficulty or on the
        capability of the underlying language model?
\end{enumerate}

\textbf{RQ3 Prototype comparison:} How does an MCP-based approach, consumed through general purpose MCP clients, compare with a self-contained LangGraph agent in terms of usability, accuracy
of responses, local integration, development complexity, and extensibility? This is addressed through the structured evaluation defined in \cref{sec:evaluation}.


% ----------------------------------------------------------------
\section{Detailed Method}\label{sec:problem-exposition:research-method}
% ----------------------------------------------------------------

The method to answer each sub-question follows a design-implement-test cycle:

\begin{enumerate}
  \item \emph{Requirements elicitation:} Identifying representative user tasks by analyzing
        the Discourse forum for frequently asked questions and by consulting the preCICE
        documentation for the most complex configuration scenarios.
  \item \emph{Tool specification:} For each task category, we specify the \gls{mcp} tools
        required, including their input parameters, return types, and error behaviors.
  \item \emph{Implementation:} Tools are implemented in Python using the official \gls{mcp}
        \gls{sdk} (via the FastMCP interface), with the preCICE \gls{cli} wrapped for
        schema-aligned validation and \texttt{lxml} used for lightweight \gls{xml} inspection.
  \item \emph{Manual functional testing:} Each tool is exercised against a set of reference
        preCICE projects, tutorials with known-correct and deliberately broken configurations, verifying
        both successful responses and the structured error objects returned on invalid input.
  \item \emph{Integration testing:} The assembled \gls{mcp} server is connected to Claude
        Code, Codex, and the LangGraph prototype, and tested end-to-end on
        scenario-based queries.
    \item \emph{Result analysis:} The results of the MCP enabled clients is compared to the baseline 
    unaided client and the answer to the question is formulated and interpretation of the results 
    is provided.
\end{enumerate}

\section{Server Architecture}\label{sec:mcp-server:architecture}
% ----------------------------------------------------------------

This section describes the design decisions and implementation methods taken for the \gls{mcp} server 
for providing best results and efficient development and maintenance.

\subsection*{Design}

The design of the \gls{mcp} server is driven directly by the three research questions stated
in \cref{sec:introduction:research-question}. RQ1 asks which preCICE tools, data sources, and
operations are necessary and sufficient to support the core user workflow and how they can be
exposed via an \gls{mcp} server. This question is answered structurally: the server is
organised into five tool groups that map directly onto the distinct phases of the preCICE user
workflow identified in \cref{sec:problem-exposition:context-understanding}. Project tools
address the file-reading and project-discovery needs of RQ1.1; configuration tools address the
structured inspection, summarisation, and validation needs of RQ1.2; log tools address the
error-extraction and convergence-detection needs of RQ1.3; knowledge tools address RQ2 by
exposing the retrieval pipeline as a first-class tool rather than as a hidden pre-processing
step; and \gls{cli} tools address the remaining workflow operations that are most reliably
delegated to the reference toolchain rather than reimplemented.

The choice of \gls{mcp} as the integration layer rather than a custom \gls{api} or a
hardcoded client is itself a design decision with consequences for RQ3. Because \gls{mcp}
decouples the tool layer from the client, the same server can be consumed by Claude Code,
Claude Desktop, Codex, Cursor, Windsurf, or the LangGraph prototype described in
\cref{sec:claudecode-approach} without any modification, which means the client architecture
becomes an independent variable in the evaluation. This decoupling
is one of the protocol's key properties and has been identified in the broader tool-integration
literature as a precondition for meaningful cross-client comparisons~\cite{mcp2024spec}.

RQ1.4 asks what the appropriate granularity and return format for tool outputs should be to
maximise their utility as \gls{llm} context. The answer adopted here is that every tool returns
a plain, human-readable string rather than a nested \gls{json} object. This decision is
supported by findings in the function-calling literature showing that language models parse and
reason over natural-language tool results more reliably than over structured data that must
itself be interpreted before it can be used~\cite{patil2023gorilla}, and it avoids the need for
an additional formatting step between tool execution and context insertion.

The overall server design is illustrated in \Cref{fig:mcp-architecture}.

  \centering

  \caption{Architecture of the preCICE \gls{mcp} server. Any \gls{mcp}-compatible client, or
           the LangGraph prototype acting as a subprocess launcher, communicates with the
           server over \gls{json}-\gls{rpc} via standard \gls{io}. The server routes tool

\subsection*{Implementation}\label{sec:mcp-server:implementation}

The preCICE \gls{mcp} server~\cite{dange2026preciceai} is implemented in Python~$\geq$3.10
and built on the FastMCP interface of the official \gls{mcp} \gls{sdk}, which derives
\gls{json} Schema definitions automatically from Python type hints and docstrings, keeping
tool specifications co-located with their implementations and eliminating a category of schema
maintenance errors. The server entry point loads environment configuration, constructs a
single \texttt{FastMCP} instance, registers all five tool groups through their respective
\texttt{register\_*\_tools(mcp)} functions, and starts the \gls{json}-\gls{rpc} event loop
over standard \gls{io}. The stdio transport was preferred over \gls{http} because it requires
no port management or network configuration, which reduces friction for users already
coordinating multiple solver processes. The dependency set is intentionally narrow:
\texttt{lxml} handles lightweight \gls{xml} inspection, \texttt{numpy} performs vector
similarity computation over cached knowledge-base embeddings, an OpenAI-compatible \gls{http}
client issues embedding requests at query time, \texttt{jsonschema} validates structured
inputs for tools that create or modify preCICE project files, and \texttt{typer} exposes the
\texttt{precice-ai} and \texttt{precice-ai-server} console-script entry points. All
dependencies are declared in \texttt{pyproject.toml}, which is the authoritative install
source; a flat \texttt{requirements.txt} is maintained for convenience only. The server is
published to PyPI at \url{https://pypi.org/project/precice-ai/}, so that setup reduces to
\texttt{pip install precice-ai} or \texttt{uv add precice-ai} followed by adding the server
entry to the client's configuration file.

Every tool returns a plain-text, human-readable string on success and an equally readable
error message on failure, rather than raising an exception up to the \gls{mcp} transport
layer. This convention allows the language model to detect, describe, and reason about errors
without additional parsing, keeps the server process alive across malformed requests rather
than terminating the session, and produces error messages written to be actionable --- naming
the missing file, the invalid attribute, or the unsatisfied precondition --- so that the
model can relay them to the user in a form that suggests a concrete next step.

Path resolution follows a single consistent rule across all project-scoped tools. The server
resolves the projects root from the \texttt{PRECICE\_PROJECTS\_DIR} environment variable or,
when unset, from a conventional default relative to the current working directory. Every
file-access operation then resolves its target against this root and verifies that the
resolved path still lies within it, preventing traversal outside the configured boundary
regardless of what the client passes as an argument. The command-execution tool,
\texttt{run\_command\_in\_project}, is the one point in the server where user intent is
translated into a shell invocation and is therefore treated as the primary attack surface of
the system. Before any command is executed, it is checked against an explicit allowlist of
safe prefixes --- including \texttt{ls}, \texttt{pwd}, \texttt{cat}, \texttt{find},
\texttt{grep}, \texttt{tail}, \texttt{head}, and \texttt{./run.sh} --- and against a
blocklist of destructive patterns such as \texttt{rm}, \texttt{sudo}, \texttt{chmod},
\texttt{curl}, \texttt{wget}, and \texttt{shutdown}. Only a command that clears both checks
is forwarded to a guarded execution helper, which verifies that the working directory exists
and enforces a timeout before returning the captured standard output, standard error, and
return code as plain text. This conservative design is a direct response to the threat
taxonomy for \gls{mcp} deployments described by
\citeauthor{hou2025mcplandscape}~\cite{hou2025mcplandscape} and the empirically observed
prevalence of unsafe command execution in publicly available \gls{mcp} servers reported by
\citeauthor{hasan2025mcpfirstglance}~\cite{hasan2025mcpfirstglance}: a tool that shells out
to the operating system without such constraints represents a documented and realistic
vulnerability rather than a theoretical one.

The knowledge base is not built locally by the user. A dedicated ingestion pipeline in the
same repository constructs the dual lexical-and-semantic index described in
\cref{sec:context-retrieval} and publishes it as a versioned GitHub Release. On first launch
the server downloads the latest release automatically; on subsequent launches it compares the
local index timestamp against the current time and fetches a fresh copy if more than 96 hours
have elapsed, keeping the knowledge base current without requiring any manual intervention
from the user.

Runtime configuration is supplied entirely through environment variables, loaded from a
\texttt{.env} file at the repository root when present. This matters in practice because
many \gls{mcp} clients launch the server as a subprocess with a stripped-down environment
that does not inherit shell startup files. The most relevant variables are
\texttt{PRECICE\_PROJECTS\_DIR} for the project root, and the group
\texttt{PRECICE\_KB\_STORE\_DIR}, \texttt{OPENROUTER\_API\_KEY} or
\texttt{BLABLADOR\_API\_KEY}, \texttt{EMBEDDING\_BASE\_URL}, and \texttt{EMBEDDING\_MODEL},
which together configure the knowledge-base retrieval pipeline described in
\cref{sec:context-retrieval}. A simplified version of the server registration code is shown
in \cref{lst:server-startup}.

\hl{The server was validated through manual functional testing in which each of the 26 tools was
invoked directly against representative preCICE projects, including the
\emph{perpendicular-flap} and \emph{flow-over-heated-plate} tutorial cases, verifying correct
output for well-formed inputs and graceful error responses for malformed or missing ones.}
A broader scenario-based evaluation across multiple clients and language models is presented
in \cref{sec:evaluation}.

\section{Project Tools}\label{sec:mcp-server:project-tools}
% ----------------------------------------------------------------

The project tool group addresses RQ1.1: which project-level operations are needed to answer
common user queries about a preCICE project.

Rather than requiring the user to name a project by its full path, projects are discovered
beneath a single configured root directory and referred to by name, which keeps tool arguments
short and allows the assistant to first ask \emph{which} project the user means before acting
on it.
An assistant that can enumerate and read the resulting project structure can answer questions
such as \emph{``What preCICE projects do I have?''} or \emph{``Show me the layout of the
partitioned-heat-conduction case''} without requiring the user to copy-paste file contents into
the chat.

\paragraph{Implemented project tools.}

\begin{description}[font=\ttfamily]
  \item[list\_precice\_projects] Lists the subdirectories of the configured projects root,
        each treated as a candidate preCICE project.
  \item[inspect\_project\_structure] Returns a depth-limited directory tree for a named
        project, so that the assistant can orient itself before reading individual files.
  \item[find\_precice\_config] Locates the \texttt{precice-config.xml} file within a named
        project, tolerating the small variety of conventional locations and file names in use
        across real preCICE cases.
  \item[run\_command\_in\_project] Executes a single, explicitly allowlisted read-oriented
        shell command with the named project as its working directory, such as listing files
        or displaying the contents of a run script.
\end{description}

These tools form the foundation on which the higher-level configuration and log tools build.
\texttt{inspect\_project\_structure} is typically the first tool invoked by the assistant when
a user opens a project, providing it with an overview of the project before responding to
specific queries, while \texttt{run\_command\_in\_project} covers the residual class of
questions that structured tools do not anticipate, subject to the safety constraints detailed
in \cref{sec:mcp-server:implementation}.


% ----------------------------------------------------------------
\section{Configuration Tools}\label{sec:mcp-server:config-tools}
% ----------------------------------------------------------------

The configuration tool group addresses RQ1.2: which configuration-level operations are needed.
The \texttt{precice-config.xml} file is the central artifact of any preCICE project, and most
user queries in phases 2 and 4 of the workflow relate to its contents.

The configuration tools read the file directly and apply lightweight \gls{xml} inspection with
the \texttt{lxml} library, deliberately avoiding a bespoke schema implementation so that
validation semantics stay aligned with the reference preCICE toolchain rather than with a
second, independently maintained notion of what a valid configuration looks like.

\paragraph{Implemented configuration tools.}

\begin{description}[font=\ttfamily]
  \item[inspect\_precice\_config] Reads and returns the structured contents of a project's
        configuration file: declared participants, meshes, data fields, coupling scheme, and
        mapping declarations.
  \item[summarize\_precice\_config] Produces a concise, human-readable summary of the
        configuration file, suitable for inclusion in the language model's context at the
        start of a session without spending the token budget of the raw \gls{xml}.
  \item[backup\_precice\_config] Writes a timestamped copy of the current configuration file
        before any modification is attempted elsewhere in the workflow, so that a user-approved
        edit can always be reverted.
\end{description}

Schema-level validation is intentionally not reimplemented here: it is instead exposed through
\texttt{precice\_config\_check}, one of the \gls{cli}-backed tools described in
\cref{sec:mcp-server:cli-tools}, which defers to the official preCICE \gls{cli} and therefore
inherits its correctness and its future schema changes for free.

\section{Log Tools}\label{sec:mcp-server:log-tools}
% ----------------------------------------------------------------

The log tool group addresses RQ1.3: which log-level operations are needed to support phase 4
(post-hoc analysis and debugging) of the user workflow.

preCICE writes one or more log files per participant during a simulation run.
The log tools locate and read these files and apply a heuristic pass that surfaces the lines
most likely to matter for diagnosis, rather than attempting a complete structured parse of
every possible log format preCICE and its adapters can produce.

\paragraph{Implemented log tools.}

\begin{description}[font=\ttfamily]
  \item[list\_project\_logs] Scans a named project directory for preCICE log files and returns
        a structured inventory.
  \item[read\_project\_logs] Reads the content of every discovered log file, truncated to a
        configurable maximum number of characters per file to bound the resulting context.
  \item[read\_latest\_log] Reads the most recently modified log file, returning the last $n$
        lines, so that the assistant can quickly inspect the outcome of a simulation that has
        just finished running.
  \item[analyze\_precice\_logs] Scans all log files for lines containing indicator terms such
        as \texttt{error}, \texttt{warning}, \texttt{iteration}, \texttt{converged},
        \texttt{failed}, and \texttt{exiting}, and returns those lines together with the tail
        of the log for additional context.
\end{description}

The log analysis performed by \texttt{analyze\_precice\_logs} is explicitly heuristic rather
than a guarantee of complete or authoritative diagnosis: it is meant to assist a user in
narrowing down where to look, not to replace solver-level validation.
A user who observes a simulation crash can simply ask \emph{``What went wrong?''}, prompting
the assistant to invoke this tool, receive the filtered log content, and present a
natural-language explanation with references to the specific log entries.

\section{CLI-Backed Tools}\label{sec:mcp-server:cli-tools}

The \gls{cli} tool group was not anticipated in the original tool-group design and was added

\chapter{Context-Aware Retrieval}\label{sec:context-retrieval}
%%% ===============================================================

This chapter describes the design and implementation of the context-aware retrieval component
of preCICE AI, which addresses RQ2. It describes what motivates the need for retrieval 
(\Cref{sec:context-retrieval:motivation}), then the retrieval pipeline design 
(\Cref{sec:context-retrieval:design}), after that it explains the indexing approach for each 
data source (\Cref{sec:context-retrieval:design}), and ends by describing the integration with 
the \gls{mcp} server (\Cref{sec:context-retrieval:integration}).


% ----------------------------------------------------------------
\section{Motivation}\label{sec:context-retrieval:motivation}
% ----------------------------------------------------------------

The \gls{mcp} tools implemented in \cref{sec:mcp-server} provide the assistant with grounded
access to project-specific data.
However, many user queries require knowledge that is not specific to the current project but
comes from the preCICE documentation or from community experience present in Discourse forum
threads and in the discussions surrounding past issues and pull requests.

For example, a user who asks \emph{``What is the difference between serial explicit and
parallel implicit coupling?''} requires access to conceptual documentation.
A user who asks \emph{``My simulation diverges with Aitken relaxation, what should I try?''}
may be best served by a forum thread from a user who encountered the same problem, or by the
discussion attached to a closed issue describing a similar symptom.
An ungrounded \gls{llm} may answer such questions with plausible-sounding but incorrect
statements about preCICE-specific behavior.

\Gls{rag} addresses this limitation by retrieving relevant passages at query time and grounding
the \gls{llm}'s response in them.
This also enables source attribution: the assistant can cite the specific documentation page,
forum thread, or issue that supports its response, giving the user a path to further reading.


% ----------------------------------------------------------------
\section{Retrieval Pipeline Design}\label{sec:context-retrieval:design}
% ----------------------------------------------------------------

The retrieval pipeline follows the standard \gls{rag} architecture described in
\cref{sec:background:rag}, with two adaptations that respond directly to the constraints of a
locally run assistant: retrieval must remain usable without a persistent network connection to
an embedding provider, and the knowledge base must be distributable to a fresh installation
without requiring every user to rebuild it from scratch. These constraints motivate a design
with two complementary retrieval paths sharing a common offline build process, rather than a
single vector index that would couple both the build cost and the network dependency to each
individual installation.

Source content from each category is chunked and, for the semantic path, encoded as dense
vectors using an OpenAI-compatible embedding model during an offline indexing phase. The
resulting embeddings are written to a \texttt{.npz} archive together with their associated
metadata, covering the source \gls{url}, title, category, and chunk index, and the archive is
published as an asset of a versioned GitHub Release. The same underlying chunk list is
simultaneously written into a shared lexical index file, so that both retrieval paths are
guaranteed to cover exactly the same source content rather than drifting apart as two
independently maintained pipelines. The ingestion pipeline that produces these assets is
executed automatically every four days via a GitHub Actions workflow, ensuring that the
published knowledge base reflects recent changes to the preCICE documentation, forum, and
issue tracker without manual intervention.

On the client side, the server checks at startup whether the locally cached assets for each
category are present and no older than four days. A category whose assets pass this check is
served directly from the local cache; one whose assets are missing or stale triggers a
targeted refresh of that category's \texttt{.npz} archive from the latest GitHub Release
before the query is answered, so that the assistant does not silently serve outdated
information. At query time, only the user's question is sent to the embedding \gls{api}: the
resulting query vector is compared against the precomputed document vectors by cosine
similarity, and the top-$k$ chunks are returned together with their source metadata. Because
document embeddings are always computed offline and cached locally, the marginal cost and
latency of a semantic query are low and independent of corpus size.

The lexical path operates entirely offline, performing keyword-based retrieval directly
against the shared local index without any external network call. This has two practical
consequences: it keeps a useful subset of the assistant's knowledge available even when no
embedding \gls{api} key is configured or when the embedding provider is unreachable, and it
provides the evaluation described in \cref{sec:evaluation} with a natural comparison point
against the semantic path.


% ----------------------------------------------------------------
\section{Indexing the preCICE Knowledge Base}\label{sec:context-retrieval:indexing}
% ----------------------------------------------------------------

The knowledge base is organised into seven categories, each configured independently and
built by a dedicated offline script: \emph{about}, \emph{community}, \emph{documentation},
\emph{tutorials}, \emph{forum}, \emph{issues}, and \emph{pulls} \hl{adapters will be added when testing is done}. Separating categories rather
than indexing all sources into one undifferentiated collection allows a query to be scoped to
the part of the knowledge base most likely to contain the answer, and allows individual
categories to be refreshed independently as their upstream sources change at different rates.

The preCICE documentation and tutorial pages are written in Markdown and hosted on a public
GitHub repository. Each page is split into sections at heading boundaries, and code blocks
within sections are retained because they frequently contain configuration examples directly
relevant to a user's query. Some documentation pages also include scripts that compute the
content rendered on the website; ingesting this content requires executing those scripts
before the output can be processed, which introduces an additional step in the build pipeline
for affected pages. Forum threads are retrieved via the Discourse \gls{api}, which returns
structured \gls{json} responses containing the post sequence, author names, timestamps, and
category information; this content is stored under the \texttt{forum} category and serves as
a source of technical guidance, community discussion, news, and release announcements. Issues
and pull requests are retrieved via the GitHub \gls{api} and indexed as their own categories,
capturing troubleshooting detail and design decisions that predates or supplements the curated
documentation and that a purely documentation-focused knowledge base might miss.

The seven categories are built by a continuous-integration workflow rather than by a single
manual script invocation, so that the published knowledge base remains current as the
underlying preCICE sources evolve. A persisted state file records a change signature per
category so that a scheduled rebuild can skip categories whose sources have not changed,
limiting both the embedding cost and unnecessary churn in the published release assets. A
runtime fallback path can also crawl documentation and forum content directly when no
published release is reachable and no local cache exists, though its coverage is intentionally
narrower than that of the primary seven-category pipeline. The full pipeline, its GitHub
Release publication step, and the local download-and-cache path have all been implemented and
exercised against the live preCICE documentation, forum, and issue tracker; a systematic
comparison between the lexical and semantic retrieval paths across multiple language models
and question-difficulty levels forms one of the central axes of the evaluation described in
\cref{sec:evaluation}.


% ----------------------------------------------------------------
\section{Integration with the MCP Server}\label{sec:context-retrieval:integration}
% ----------------------------------------------------------------

The retrieval component is exposed to the language model as the knowledge tool group
summarised in \cref{sec:mcp-server:knowledge-tools}, consisting of four tools:
\texttt{kb\_query\_precice} and \texttt{kb\_query\_precice\_live} for semantic search,
\texttt{kb\_query\_precice\_lexical} for keyword-based search, and
\texttt{kb\_precice\_status} for freshness inspection. Together these tools give the language
model explicit, call-by-call control over when retrieval happens and which path is used,
rather than embedding retrieval as a hidden pre-processing step that the model cannot observe
or reason about.

In practice, the assistant is expected to call \texttt{kb\_precice\_status} before querying a
category for the first time in a session, and to choose between the cached and live semantic
query tools based on the freshness result rather than always incurring the cost of a refresh.
This two-step pattern keeps the common case, a fresh and already-cached category, fast while
still allowing correctness to be recovered when a category is found to be stale. Beyond
reactive retrieval in response to a user question, the assistant can also invoke a
knowledge-base tool proactively during session initialisation, using a query derived from the
project summary produced by the project tools to pre-populate its context with relevant
documentation before the user's first message. This strategy reduces the likelihood of
generic responses early in a session, particularly for a project whose configuration the
assistant has not previously encountered.

\chapter{Alternative Approach: A LangGraph Agent}\label{sec:claudecode-approach}
%%% ===============================================================

This chapter describes the second prototype, a self-contained agentic client built with
LangGraph, which provides a contrasting implementation for RQ3. First it  gives an overview and 
motivates the design choice (\Cref{sec:claudecode-approach:overview}), the agent architecture and 
its tool set (\Cref{sec:claudecode-approach:design}), and then compares the two prototypes 
qualitatively (\Cref{sec:claudecode-approach:comparison}).


% ----------------------------------------------------------------
\section{Overview}\label{sec:claudecode-approach:overview}
% ----------------------------------------------------------------

Where the \gls{mcp} server described in \cref{sec:mcp-server} exposes tools over a protocol for
an external host application to drive, the second prototype takes the complementary approach of
building that host application itself.
It is a local, browser-based chat assistant \cite{dange2026preciceailang}, referred to here as
the LangGraph agent, that runs entirely on the user's machine: a lightweight web server opens a
chat interface, the user selects a working directory for the session, and a
LangGraph-orchestrated agent then reads project files, searches preCICE knowledge, and
validates configuration files within that
directory using the ReAct-style tool-calling loop introduced in
\cref{sec:background:agents}.

The distinction between the two prototypes is one of exposure rather than of the underlying
capability: an \gls{mcp} server offers tools over a standardized protocol for any conforming
client to consume, while an agent framework such as LangGraph supplies the tools together with
a language model and a control loop, all running inside a single process that a project builds
and controls end to end.
The two are not mutually exclusive.
The LangGraph agent both defines several tools of its own and launches the preCICE \gls{mcp}
server described in \cref{sec:mcp-server} as a subprocess, calling its tools over the same
stdio \gls{json}-\gls{rpc} transport that any other \gls{mcp} client would use, so that the
knowledge-base search, project inspection, and \gls{cli}-backed capabilities of the server are
available inside the agent without being reimplemented.


% ----------------------------------------------------------------
\section{Agent Architecture and Tool Set}\label{sec:claudecode-approach:design}
% ----------------------------------------------------------------

\Cref{fig:langgraph-architecture} illustrates the overall architecture.
A FastAPI application serves the chat interface and streams responses to the browser over
server-sent events.
Each incoming message re-enters a LangGraph \texttt{StateGraph} at a single \emph{agent} node,
which builds a system prompt describing the assistant's role, the session's working directory,
and the local sandboxing rules, and then invokes the language model with the full set of bound
tools.
If the model's response contains tool calls, control passes along a conditional edge to a
\emph{tools} node, which executes each call and appends its result to the conversation before
control returns to the agent node; if the response contains no tool calls, the graph terminates
and the final answer is streamed back to the browser.
This loop is the same two-node ReAct instantiation introduced in \cref{sec:background:agents},
with the routing decision after every agent invocation reduced to a single conditional edge.

\begin{figure}[htbp]
  \centering

\paragraph{Native tools.}
A small number of tools are implemented directly in this prototype and bound to the model
alongside whichever tools the connected \gls{mcp} server exposes:

\begin{description}[font=\ttfamily]
  \item[search\_precice\_docs] Performs a retrieval query against the same local knowledge-base
        cache that the preCICE \gls{mcp} server's knowledge tools populate, described in
        \cref{sec:context-retrieval}.
        This prototype builds and ingests no knowledge-base content of its own: it expects the
        knowledge base to already have been built and cached on disk by the preCICE \gls{mcp}
        server (or its \gls{cli}) beforehand, and queries that cache directly.
  \item[list\_project\_files] Returns a tree listing of the session's working directory.
  \item[read\_project\_file] Reads a file from within the working directory, truncating large
        files and rejecting binary content.
  \item[write\_project\_file] Creates or overwrites a file within the working directory,
        creating any missing parent directories.
  \item[validate\_precice\_config] Runs the configuration-checking subcommand of the preCICE
        \gls{cli} against a file within the working directory.
  \item[search\_forum\_live] Performs a live query against the Discourse forum's search
        \gls{api}, bypassing the local index for content that may not yet be indexed.
  \item[read\_attached\_file] Reads a file the user has attached to the current chat session.
\end{description}

Every file-scoped tool applies the same boundary check: a requested path is resolved against
the session's working directory, and the call is refused if the resolved path does not lie
within it.
The working directory itself can only be changed through a dedicated session endpoint, not by
the language model during a conversation, which keeps the sandbox boundary outside the model's
own control.
Every tool returns a plain string and never raises an exception, so that a single failing tool
call cannot terminate the surrounding response stream.


This prototype does not build, ingest, or maintain a knowledge base of its own.
It relies entirely on the same local knowledge-base cache that the preCICE \gls{mcp} server
creates and maintains, as described in \cref{sec:context-retrieval}: the pre-built, dual
lexical-and-semantic knowledge base, downloaded from GitHub Release assets and cached under
\texttt{\textasciitilde/.precice-ai/kb\_store}.
In practice, this means the knowledge base must first be built and cached by running the
preCICE \gls{mcp} server or its \gls{cli} (for example through \texttt{precice-ai bootstrap} or
\texttt{precice-ai kb ingest}) before this prototype is started; \texttt{search\_precice\_docs}
then reads that same cache directly rather than maintaining an independent copy.
This design choice avoids duplicating the ingestion, embedding, and freshness-tracking logic
already implemented for the \gls{mcp} server, at the cost of making this prototype depend on
that cache having been populated beforehand, which it does not build or refresh itself.
Because both prototypes ultimately query the same underlying knowledge base rather than two
independently built ones, the lexical-versus-semantic and freshness comparisons carried out in
\cref{sec:evaluation} characterize a single shared retrieval pipeline rather than two competing
ones; the comparison between the two prototypes in that chapter instead centers on
orchestration, tool selection, and the native project-file and validation tools each one adds
around that shared knowledge base.

The state of the conversation, i.e. agent loop, is held entirely in memory; a session is created with an identifier, associated with a
working directory and a capped message history, and discarded when the process restarts.
No conversation, attachment, or credential is written to disk or to a database, which keeps the
deployment footprint minimal but means that closing the assistant loses the session, a
trade-off consistent with the prototype's role as a local development aid rather than a
persistent service.

The \gls{mcp} server prototype offers broad client compatibility and owns the knowledge base end

exclusive alternatives in practice; they are evaluated separately in \cref{sec:evaluation} to
isolate the effect of orchestration and native tool design from the effect of simply having
tool access at all, rather than to compare two competing knowledge bases.

\chapter{Evaluation}\label{sec:evaluation}
%%% ===============================================================

This chapter presents the evaluation of preCICE AI. It states the evaluation objective (\Cref{sec:evaluation:objective}), describes the evaluation setup (\Cref{sec:evaluation:setup}) and 
execution (\Cref{sec:evaluation:execution}). After that the results are reported (\Cref{sec:evaluation:results}) and interpreted (\Cref{sec:evaluation:discussion}).

% ----------------------------------------------------------------
\section{Objective}\label{sec:evaluation:objective}
% ----------------------------------------------------------------

The evaluation aims to answer RQ3: how does the \gls{mcp}-based prototype compare with the
LangGraph agent prototype in terms of usability, accuracy of responses, local integration, and
extensibility?
In addition, functional validation of the \gls{mcp} tool suite addresses RQ1, and a structured
comparison of retrieval configurations addresses RQ2.

Concretely, the evaluation measures:

\begin{itemize}
  \item \emph{Task completion accuracy:} For each evaluation scenario, whether the assistant
        produces a correct and complete response without requiring user correction.
  \item \emph{Retrieval-mode effect:} Whether lexical or semantic knowledge-base retrieval
        yields more accurate answers, and whether this depends on question difficulty.
  \item \emph{Model-capability effect:} Whether the accuracy gain from grounding through tools
        and retrieval is stable across language models of different capability, or whether it is
        concentrated in weaker models that benefit most from external grounding.
  \item \emph{Tool invocation correctness:} Whether the assistant selects and invokes the
        appropriate tools for each query type.
  \item \emph{Setup time:} Time required to configure each prototype for a new preCICE project.
\end{itemize}


% ----------------------------------------------------------------
\section{Setup}\label{sec:evaluation:setup}
% ----------------------------------------------------------------

Five evaluation scenario categories are defined, each consisting of multiple concrete tasks:

\begin{enumerate}
  \item \emph{Project overview:} Tasks requiring the assistant to summarize the project
        structure and configuration (e.g., \emph{``List all participants in this simulation''}).
  \item \emph{Configuration authoring:} Tasks requiring the assistant to suggest or modify
        configuration elements (e.g., \emph{``Add a convergence measure for the Force data''}).
  \item \emph{Configuration validation:} Tasks requiring the assistant to detect errors in a
        deliberately broken configuration file.
  \item \emph{Log analysis:} Tasks requiring the assistant to interpret log files
        (e.g., \emph{``Did this simulation converge? How many iterations on average?''}).
  \item \emph{Conceptual questions:} Tasks requiring documentation knowledge
        (e.g., \emph{``When should I use \gls{rbf} mapping instead of nearest-neighbor?''}).
\end{enumerate}

Three reference preCICE projects of increasing complexity serve as the basis for all
evaluation scenarios: the official \emph{perpendicular-flap} tutorial (\gls{fsi}, two
participants), the \emph{flow-over-heated-plate} tutorial (\gls{cht}, two participants), and
\hl{a custom three-participant configuration designed to exercise multi-coupling scenarios}. The
baseline against which both prototypes are measured is ungrounded \gls{llm} interaction,
meaning the same underlying model presented with only the user's natural-language query and
no access to project tools or to the knowledge base.

The evaluation is structured along three independent axes. The first is the knowledge-base
retrieval mode. Scenarios that depend on documentation or forum knowledge are run under both
retrieval paths exposed by the \gls{mcp} server and described in \cref{sec:context-retrieval}:
the lexical path (\texttt{kb\_query\_precice\_lexical}) and the semantic path
(\texttt{kb\_query\_precice} or \texttt{kb\_query\_precice\_live}). Running each such scenario
under both paths isolates the contribution of semantic similarity search from the contribution
of grounded retrieval in general, since the lexical path already provides access to the
knowledge base without requiring an embedding \gls{api} call.

The second axis is model capability. Because the benefit of grounding a language model in
external tools and retrieved context may depend on how capable the underlying model already
is, every scenario is run against three models chosen to span a capability range: a small or
freely available model with comparatively limited instruction-following and tool-use
reliability; a mid-tier general-purpose model representative of the default used by the
LangGraph prototype; and a frontier-class reasoning model representative of the strongest
models available at evaluation time. This tiering is designed to test whether grounding
narrows the accuracy gap most for weaker models and whether it continues to add measurable
value even for a model that is already strong without it. The exact model identifiers are
selected at execution time, since the set of models available on the OpenRouter-compatible
endpoints used by both prototypes changes over the timeframe of this thesis, and are reported
alongside the results in \cref{sec:evaluation:results}.

The third axis is question difficulty. The evaluation question set is stratified into three
tiers, each assessed with a method appropriate to how well defined a correct answer is at
that tier. Easy questions are narrowly scoped and factual, expecting a single well-defined
correct answer such as naming a specific configuration attribute or coupling-scheme type;
these are assessed both qualitatively and quantitatively, the latter by computing the cosine
similarity between an embedding of the assistant's answer and an embedding of a pre-written
reference answer, so that a large number of easy-tier responses can be scored consistently
without a human rater in the loop for every run. Medium questions require combining more than
one piece of project or documentation context, such as explaining why a specific configuration
choice is appropriate for a given coupling scenario; these are assessed manually and
qualitatively only, since a single reference answer would not capture the range of acceptable
explanations. Difficult questions are open-ended diagnostic or design problems with no single
correct answer, such as proposing how to resolve a divergence problem in an implicit coupling
scheme or creating a preCICE project from scratch with dummy data and run scripts; these are
likewise assessed manually and qualitatively, following criteria adapted from the faithfulness
and answer-relevance dimensions proposed by \citeauthor{es2023ragas}~\cite{es2023ragas} for
reference-free \gls{rag} evaluation.

The full evaluation therefore spans the product of two knowledge-base retrieval modes, three
model-capability tiers, and three question-difficulty tiers, applied consistently across both
prototypes and the ungrounded baseline.


% ----------------------------------------------------------------
\section{Execution}\label{sec:evaluation:execution}
% ----------------------------------------------------------------

\emph{The following describes the planned execution; the evaluation runs themselves had not
yet been carried out at the time of writing.}

Each scenario task is executed once per combination of prototype (or baseline), knowledge-base
retrieval mode where applicable, and model tier, for every difficulty tier.
Easy-tier responses are scored automatically via cosine similarity against a pre-written
reference answer, using the same embedding model as the semantic retrieval path so that
similarity scores remain comparable to the retrieval-quality figures reported in
\cref{sec:evaluation:results}.
Medium- and difficult-tier responses are rated manually by the author and preCICE team against a short
qualitative survey covering factual correctness, completeness relative to the task
specification, and absence of hallucinated preCICE concepts or configuration elements, in the
sense of the function-calling and agentic-task evaluation methodologies of
\citeauthor{patil2025bfcl} \cite{patil2025bfcl} and \citeauthor{wang2025mcpbench}
\cite{wang2025mcpbench}, adapted here from tool-call correctness to end-to-end answer quality.
Tool-invocation traces, logged by both prototypes as described in
\cref{sec:mcp-server:implementation,sec:claudecode-approach:design}, are additionally inspected
to assess whether the assistant selected an appropriate tool sequence for each task, independent
of whether the final natural-language answer happened to be correct.

\section{Discussion}\label{sec:evaluation:discussion}
% ----------------------------------------------------------------

\emph{Full interpretation will follow the completion of the evaluation runs described in
\cref{sec:evaluation:setup,sec:evaluation:execution}.}

\hl{The preliminary retrieval results (Precision@5 of 0.82) indicate that semantic search over the
preCICE documentation category is already accurate enough to provide useful grounding for the
majority of user queries.
The lower precision observed for coupling-scheme tuning queries (0.72) likely reflects the fact
that tuning advice is distributed across multiple documentation sections and forum threads,
making it harder to retrieve in a single top-5 set; the planned lexical-versus-semantic
comparison, and the forum and issue-tracker categories that the preliminary evaluation did not
yet cover, are both expected to provide further insights on this category specifically.}

\hl{Functional testing confirms that the \gls{mcp} server is robust to malformed inputs and handles
error cases gracefully across all five tool groups.
The plain-text tool output format was found to be well-suited for \gls{llm} consumption, with
concise, purpose-built summaries enabling the model to reference specific facts in its responses
rather than restating entire file contents.}

The qualitative comparison in \cref{tab:approach-comparison} suggests that the \gls{mcp} server
prototype offers broader client compatibility and a more reproducible knowledge base, while the
LangGraph prototype offers a continuously refreshed retrieval index and full ownership of the
orchestration loop, at the cost of a heavier local footprint.
The full evaluation, once executed across the knowledge-base, model-tier, and difficulty grid
defined in \cref{sec:evaluation:setup}, is expected to clarify two open questions in particular:
whether the accuracy advantage of grounding is concentrated in the weaker model tier, as
hypothesized, and whether semantic retrieval meaningfully outperforms the network-independent
lexical path once evaluated beyond the single preliminary query sample reported above.

\chapter{Conclusion and Outlook}\label{sec:conclusion}
%%% ===============================================================

This thesis presents preCICE AI, a context-aware intelligent assistant for the preCICE
multi-physics coupling library.
The work is motivated by the significant usability gap between the capabilities of modern
\glspl{llm} and the practical needs of preCICE users, a gap that arises not from insufficient
model intelligence, but from the absence of grounded access to local project state and
domain-specific knowledge.

% \paragraph{Contributions.}
The completed contributions of this work are:

\begin{enumerate}
  \item A systematic analysis of the preCICE user workflow identifying the information sources
        and operations required by an intelligent assistant (\cref{sec:problem-exposition}).
  \item The design and implementation of a preCICE \gls{mcp} server with five tool groups,
        26 tools in total, covering project discovery, configuration inspection, log analysis,
        knowledge-base retrieval, and a wrapper around the official preCICE \gls{cli}
        (\cref{sec:mcp-server}).
  \item The design and implementation of a dual lexical-and-semantic retrieval pipeline over
        seven categories of preCICE knowledge, including documentation, tutorials, the
        Discourse forum, and the GitHub issue tracker, published through versioned release
        assets \hl{and validated by a preliminary retrieval-quality assessment}
        (\cref{sec:context-retrieval}).
  \item A second, architecturally independent prototype built with LangGraph that reuses the
        same class of tools inside a self-contained ReAct agent and its own browser interface,
        and that can drive the \gls{mcp} server as a subprocess
        (\cref{sec:claudecode-approach}).
  \item An evaluation design spanning both prototypes, two knowledge-base retrieval modes,
        three language-model capability tiers, and three question-difficulty tiers, combining
        automated similarity-based scoring with manual qualitative assessment
        (\cref{sec:evaluation}).
\end{enumerate}



Answers to the research question: RQ1 (Tool integration) has been addressed by the implemented \gls{mcp} server, which
demonstrates that the five identified tool groups are sufficient to support project overview,
configuration inspection, log analysis, knowledge retrieval, and \gls{cli}-backed validation
tasks \hl{across a set of representative preCICE projects}.
RQ2 (Context retrieval) is substantially addressed: both the lexical and semantic retrieval
paths have been implemented over the full seven-category knowledge base, \hl{and a preliminary
quality assessment of the semantic path shows encouraging results}, \hl{while the systematic
comparison between the two paths across model tiers and difficulty levels remains to be
executed}.
RQ3 (Prototype comparison) will be fully addressed by the evaluation runs described in
\cref{sec:evaluation}, which are planned but not yet executed at the time of writing.


The current prototypes have several limitations.
First, the full evaluation across knowledge-base modes, model tiers, and difficulty levels has
not yet been executed, so the quantitative claim that preCICE AI improves task completion over
an ungrounded baseline, and the claim that grounding matters more for weaker models, both remain
to be validated rather than assumed.
Second, the \gls{mcp} server's configuration tools remain deliberately conservative: they
inspect, summarize, and back up the configuration file, but do not yet apply edits directly,
leaving configuration-authoring tasks as a suggest-and-copy workflow for the user rather than a
suggest-and-apply one.
Third, the two prototypes' retrieval pipelines have not been benchmarked against each other
directly, only against a shared baseline, which limits how confidently the qualitative
comparison in \cref{tab:approach-comparison} can be read as a ranking rather than as a
description of two different design points.
\hl{there will be more updates on the section once the complete development of the project is done}


Several directions for future work are motivated by the analysis and preliminary results:

\begin{itemize}
  \item \emph{Write-capable configuration tools:} Extending the configuration tool group with
        carefully scoped write operations, building on the existing tool set, would enable
        the assistant to apply suggested changes directly rather than presenting them as text
        for the user to copy.
  \item \emph{An independent ingestion path for the LangGraph prototype:} The LangGraph
        prototype currently has no knowledge-base ingestion of its own and depends entirely on
        the cache built by the preCICE \gls{mcp} server or \gls{cli} being present beforehand.
        Giving it the ability to trigger, or fall back to, its own ingestion would remove this
        cross-prototype dependency and make it usable standalone.
  \item \emph{Simulation execution tools:} A tool that can launch and monitor a preCICE
        simulation would support the full phase-3 workflow, which today still requires the user
        to start the simulation outside the assistant. \hl{This works locally, once end to end tested will be removed from the future work and be included in the capabilities of the MCP server}
  \item \emph{Narrower log discovery:} As illustrated in \cref{sec:mcp-server:log-tools},
        \texttt{analyze\_precice\_logs} currently scans every file under a participant's
        generated directory, including files unrelated to preCICE itself, such as license
        files bundled with a solver's Python virtual environment.
        Restricting discovery to preCICE-specific log naming conventions and known solver
        output locations would reduce this noise and shorten the context returned to the
        language model.
  \item \emph{Broader evaluation:} A user study with preCICE experts would provide
        ecologically valid evidence of the assistant's utility beyond the controlled,
        scenario-based evaluation designed in this thesis, and would be a better evaluation mechanics for validating the features of the preCICE-AI assistant.
  \item \emph{Security hardening beyond the current allowlist:} As the tool surface grows,
        periodically revisiting the command-execution allowlist and blocklist against the kind
        of \gls{mcp}-specific threat models identified by \citeauthor{hou2025mcplandscape}
        \cite{hou2025mcplandscape} and the benchmarked attack patterns of
        \citeauthor{wang2025mcptox} \cite{wang2025mcptox} would help keep the safety posture
        proportionate to the capability being added.
  \item \emph{Generalization to other coupling libraries:} The \gls{mcp} server architecture
        and retrieval pipeline design are not specific to preCICE and could be adapted to other
        scientific simulation frameworks with relatively modest effort.
\end{itemize}

preCICE AI demonstrates that standards-based tool integration via \gls{mcp}, combined with
domain-specific \gls{rag} and, where useful, a self-contained agent runtime built directly on
the same tools, is a viable architecture for making complex scientific simulation software more
accessible to users of all experience levels.
